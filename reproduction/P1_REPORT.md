# P1 验证与修复报告

日期：2026-11-17。作者版本：`7a813d9c2b6c73d1066eeff49b67794318f682bd`。修复位于 `repro/cpu`；作者 master、固定提交和独立原版 worktree 保留。

## 结论

三项初始疑点均由实际生产代码的最小用例确认。修复版通过 164 项常规检查；同一套用例在作者原版上为 131 通过、33 失败。另有 5 项非法输入拒绝检查及 1 项大工作区实际计算。ASan/UBSan 构建也通过这些检查，未发现 sanitizer 错误。

这仅是 **I2_V_4 的 P1 正确性验收**，不是全部格式、真实模型质量或性能验收。没有下载模型，没有运行其他框架对比，没有宣称加速收益。

## 1. 跨 token tile 的地址错误

- 位置：`ggml/src/ggml-cpu/ggml-cpu.c`，`ggml_compute_forward_mul_mat`。
- 输入：K=16，N=33，M=7；确定性权重/激活，工作区填入已知非零值；线程 1/2/4。
- 观察：原版示例输出 -19，参考结果 237；N≤32 对应检查通过。
- 原因：布局应为 `[tile][K][32]`，第 i 块的起点应为 `i*K*32`；作者调用量化时使用 `i*32`。第二块写入会与第一块数据交叠，而内核仍按 `i*K*32` 读取。多线程时交叠还可能形成竞争。
- 修复：补齐 K 步长；按 token 列分工，补齐列显式写零；保持有效 token 的 scale 独立。
- 回归：N=1/2/8/16/31/32/33/63/64/65，线程 1/2/4，非整齐 M，K=528 的分段/尾部组合。

表面上“能运行”的 N=33 测试曾会读取错误但合法地址，因此只依赖 ASan 找不到这种数值错误；标量 oracle 必不可少。

## 2. 负值量化及微小激活失真

- 位置：`ggml-cpu-quants-vlut.c`，`quantize_row_i8_v_tile`。
- 输入：`[-127,-64,-1,0]`。
- 观察：原版首项量化成 -128，scale≈7.87402e-8，重建误差约 127；允许的半步长约 0.5。负峰值占优及约 1e-8 的微小输入同样失败。
- 原因：作者取正向 max，而非绝对值最大值；负数被严重截断。另一个固定 epsilon 限制倒数，会把小幅值输入舍入成 0。
- 修复：绝对值最大值、对称 [-127,127] 量化；全零特判；非零数据用存储后的 scale 算倒数，避免前后缩放语义不一致。scale 最低为 FLT_MIN，极端 subnormal 按这个实际步长约束误差；非有限输入显式拒绝。
- 回归：全零、全负、负峰值占优、正值、微小值、大幅值、subnormal；检查写入间隔之外的保护值未变。

改变的是激活量化语义，不是简单的内存修补。因此未来模型质量与性能都要重新测试，不能直接沿用作者结果。

## 3. INT16 先溢出，INT32 后提升无法补救

- 位置：`ggml_gemm_i2v4_i8v_lut`。
- 独立输入：K=512、N=M=1，权重全 +1，激活直接提供 INT8 +127，scale=1；绕过量化和图布局。
- 观察：期望 `512×127=65024`，原版输出 -512。权重 -1、激活 -128 时应为 65536，原版为 0。
- 原因：原版每累计 512 个 K 项才从 INT16 转 INT32。中间值已超出 [-32768,32767]。
- 修复：I2_V_4 的累加段改成 128。每项最大绝对值 128，段内最坏幅值为 16384；所有前缀和也受此界限约束。128 是 16 的倍数，维持四张表的 K tile。总 K 限制在 INT32 安全范围内。
- 为什么不选 256：如果输入原始 INT8 允许 -128，`(-1)×(-128)×256=32768` 仍超出正上界。实际测试覆盖该反例。
- 回归：多个 K 边界、尾段、正/负同号极值和独立 INT64 参考。更频繁提升/清零的性能成本尚未测量。

## 4. 额外修复：工作区与多切片

**工作区不足：**原版通过固定 15000/2048 的常数补充工作区。K=16384、N=1 时，实际规划 504644 字节，但 INT8 tile 加 scale 至少需要 524292 字节。P1 原版仅检查容量，不故意触发原版越界。修复为按 padded N、K 和 scale 精确规划；修复版实际执行该形状，并通过 sanitizer。

**切片复用：**原版先对多个激活切片反复写同一缓冲区，然后只计算一次；输出也未移动到各切片位置。独立 N=1、两切片用例中，原版一处输出 50，期望 -182，因此该问题不依赖跨 N=32 的地址错误。修复为逐切片量化、屏障、计算、输出到对应切片，再同步复用工作区。

**权重形状约束：**I2_V_4 实际打包/读取粒度为 16 个 K 元素，原有 `%4` 判断不足。修复版打包和内核都明确拒绝 K=4/20 等不支持形状，并拒绝超过 INT32 范围的 K。它们是有意触发的 GGML_ASSERT，不是测试崩溃。

## 5. 验证方法与证据

入口：[test_p1.cpp](test_p1.cpp)、[run-p1.sh](run-p1.sh)、[check_results.py](check_results.py)。

- 使用同一测试源分别链接作者原版与开发版库。
- 打包解码采用独立三进制解释；整数参考用 INT64 标量乘加。
- 集成测试使用相同量化激活作 oracle；量化自身另测误差界限。
- 工作区预填非零值，并检查保护字节，避免全零初始化掩盖错误地址。
- 普通构建和 ASan/UBSan 构建分开保存；无错误输出才能判通过。
- 原版命令退出 1，代表发现数值反例；包装脚本确认预期反例存在后才标记“反例复现成功”。`author/summary.json` 的 passed=true **不代表原版正确**。
- 可公开输出在 [evidence](evidence/)。本机完整编译/环境日志保留在项目结果目录，未公开凭据或本机操作规范。

## 6. 尚未覆盖

- I1 及其他 I2 tile 变体：共享量化/图修复生效，但其他内核的 INT16 段长仍待对应阶段处理，不能认为已修复所有格式。
- 非有限激活、超大张量、任意非连续 strides/高维组合不是本次有效输入承诺；形状回归主要覆盖所列场景。
- 没有 ThreadSanitizer 证据；多线程结果通过不等于完整并发形式化证明。
- 没有真实 GGUF 模型生成质量、Prefill/Decode 吞吐、功耗或微创新收益。
