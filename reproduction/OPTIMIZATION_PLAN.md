# P2 后的小优化方案：I2_V_4 分块提升与转置

更新时间：2026-11-17。状态：**P3/P4 完成后已按用户指令实现，默认 OFF，结果见 P6_REPORT.md**。总路线见 EXECUTION_ROADMAP.md；本文件保留候选推理与完整验证目标，实际最小动机实验范围见 P6_METHOD.md。

## 1. 选择什么，为什么

选定 **只为 I2_V_4 增加按输出行分块的 INT16→INT32 提升转置**。第一版只改访问顺序，保留原来的 memset，不融合清零、不改变累加块 K=128、不改量化或权重布局，不引入新的库和硬件要求。

理由：正式首轮诊断中，N=32/128 的代表案例，原“提升/转置/清零”合计约占单线程被计时工作阶段的 32%–46%，是与查表同量级的成本；malloc/free 占比不到 1%，工作区复用优先级低。N=1 中这部分只有约 6%–7%，因此不把短输入作为本方向的主要预期受益场景。详细拆分清零后的证据会补入 P2_REPORT.md；这些百分比来自插桩诊断，并不是正式无插桩总墙钟占比的精确估计。

这是普通循环局部性优化的候选应用，**尚不能称为新研究贡献**。先核对最近邻及论文现有功能，再验证是否有净收益；不把 bug 修复或常见分块技巧包装为创新。

## 2. 现在到底做了什么

核心文件：[ggml-cpu-quants-vlut.c](../ggml/src/ggml-cpu/ggml-cpu-quants-vlut.c)。共享宏 `ACCUMULATE_TABLE_TRANS` 当前逻辑为：

```cpp
for (int j = 0; j < valid_tokens; ++j) {
    for (int i = 0; i < rows; ++i) {
        sum_i32[(token_tile * 32 + j) * rows + i] +=
            (int32_t) sum_i16[i * 32 + j];
    }
}
// 调用者接着做整个 INT16 工作区清零
memset(sum_i16, 0, sizeof(int16_t) * 32 * rows);
```

`sum_i16` 是 `[输出行][token]`，`sum_i32` 是 `[token][输出行]`。这里并非单纯把每个数从 16 位变成 32 位：它还把矩阵转置，并加到已有的 INT32 累加值上。每个 K=128 的分组结束后都做一次。

当前内层 i 前进时，源读取间隔是 32×2=64 字节；下一 token j 又遍历全部输出行。例如单线程 M=8192，INT16 工作区有 512 KiB；一个 token 遍历各行中的一个元素，然后才处理下一 token。这里存在改善访问局部性的机会。**这只是代码访问模式，未测得 cache miss，不能直接说已经证明缓存抖动。**

每个 token tile 的分组数为 ceil(K/128)；上述 6 种形状的 K 是 128 的整数倍。提升阶段只处理有效 token，清零则处理完整的 32 lane 工作区。所以尾块和 N=1 中两部分的比例可能与整块差异明显，需要拆开计时。

## 3. 准备改哪里

不要直接修改被 I1/其他 I2 共用的宏。新增一个本文件内部的 `static inline` helper，例如 `vlut_accumulate_i2v4_blocked()`，仅将 `ggml_gemm_i2v4_i8v_lut` 中四处 `ACCUMULATE_TABLE_TRANS` 调用切换到它：完整 token tile/尾 tile × 完整 K 分组/余数组。

第一版固定输出行块 B=16，示意如下（实际用 TABLE_ENTRY_SIZE，不硬编码 32）：

```cpp
for (int i0 = 0; i0 < rows; i0 += 16) {
    const int iend = min(i0 + 16, rows);
    for (int j = 0; j < valid_tokens; ++j) {
        for (int i = i0; i < iend; ++i) {
            dst[(token_tile * T + j) * rows + i] +=
                (int32_t) src[i * T + j];
        }
    }
}
```

同一个 16 行源块的全部 token 紧邻处理，T=32 时源块仅 16×32×2=1024 字节，有机会在较小工作集中完成读取；每次输出仍写连续的 16 个 INT32。只改变循环遍历顺序，保留每个元素的有符号提升和加法。

用独立编译开关 `VLUT_I2V4_BLOCKED_WIDEN=OFF/ON`（已实现，默认 OFF）保留旧路径。每个构建记录开关和 SHA；默认先 OFF。第一轮固定 B=16，不同时扫描大量块长，不同时改激活转换或清零，避免无法解释收益来源。

不需要修改 `ggml-cpu.c` 的量化/线程分发、模型文件、打包格式、LUT 建表或查表宏。新增代码预计仅局部 helper、四处调用选择和一个 CMake 开关；这是工作量估计，未承诺已经实现。

## 4. 为什么可能有效，也可能无效

- 有利点：把原先跨全部行、反复访问的源数组变为小块内复用；减少一次遍历的工作集，有利于编译器优化，避免手写 AVX2 转置的高实现成本。
- 代价：目的数组原来沿整行连续写，现在变为分段写，可能损害目的局部性；循环数量增加，线程分到很少输出行时可能没有好处。
- 不能消除的成本：INT32 目的值仍需读、加、写，K 分组次数仍相同，清零仍存在。即使分段耗时改善，图级总时间也未必改善。
- 不选“直接加大 K 分组”：K=512 已有溢出反例；不能以取消安全约束换速度。第一版不引入新的数值范围风险。
- 暂不融合清零：融合会改变两个变量，也可能给原来有效的批量 memset 增加分散写入。先由拆分数据判断其上界，再独立决定是否做第二个实验。

## 5. 如何验证

1. **独立正确性**：新增 helper 与原循环逐元素核对，覆盖 rows=1/3/5/15/16/17/31/32/81、有效 token=1/8/16/31/32、非零 dst 初值、INT16 正负极值，以及 canary 边界。测试用安全范围内的初值，避免参考实现自身溢出。
2. **真实内核回归**：OFF/ON 两个版本都通过现有 164 项 P1、5 个非法输入拒绝、大工作区、多切片、线程 1/2/4；ON 再跑 ASan/UBSan。四个替换位置以及 K 余数组、N 尾块都必须命中。
3. **分段动机实验**：仅用于诊断，查看 widen 与 clear 各自变化；预期主要改善 widen，不把插桩图当正式速度比较。若 widen 没改善，先停下来检查访问模式，不叠加第二项优化。
4. **总算子性能**：只比较同系统“正确性修复基线”与“基线+这一项优化”；normal 无插桩、相同输入、相同 CPU places/线程和编译参数，每配置至少 5 次、每样本约 1 秒；基线/优化按 ABBA 或交错顺序，至少两个独立运行批次。
5. **完整场景**：六种形状和全部 N；重点 N=32/128/256/512、M=3200/8192/8640，同时报告 N=1、尾块及不整齐 rows 的退化情况。不能只选受益最好的配置。
6. **统计与停止**：保留原始样本，报告成对延迟比、中位数、波动和置信区间；收益应超过同配置基线重测噪声，并在第二个批次重复出现。先在主要判定配置确认基线足够稳定（以 CV≤5% 为目标），如果环境波动无法收敛，就标为无法判断小收益，不继续挑选最快样本。总 graph 无稳定收益，或只剩小于噪声的差距，就停止，不宣称成功。新增持续的明显回退也要报告并决定回退，而不是悄悄隐藏场景。
7. **之后才谈模型**：内核有净收益后，复用 P3 的真实 I2 模型验证 Prefill/Decode；单算子加速不能替代模型加速。研究新颖性另做相关文献查重。

## 6. 和原路线的关系

原来的主路线仍为 P3 真实模型 → P4 I1 → P5 深化/文献 → P6 实现。本轮已先完成 BitNet I2 扩展和 I1 独立验收，再核对十项文献来源/两套代码，之后才实现本候选；没有将 P6 前移。实际执行先用八配置门槛实验，若明显无收益或回退则停止，不机械完成全部形状扫描。最终结论见 P6_REPORT.md。

## 7. 最终拆分证据

详细运行 `p2-20261117-203434-396`：N=32/128 的单线程代表案例，提升转置占 30.7%–37.3%，清零占 1.9%–2.5%。比合并计时更直接支持优先改变提升转置访问顺序。逐形状 µs 与多线程份额见 P2_REPORT.md 第 7 节；这是诊断，不是已有优化收益。
